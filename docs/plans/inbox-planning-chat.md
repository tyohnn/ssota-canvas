좋아 이제 논의하고 싶은걸 말해줄게.
쏘타가 가려는 방향은 궁극적으로 클로드 코드 GUI 버전이야. 클로드 코드는 코딩 에이전트로 시작했지만, 코드는 디지털 세상에서 원형이기 때문에 PDF, 상세페이지, 카드뉴스, 디자인, 앱, 비디오 등 다양한 결과물을 만들어내고, 사실상 업무 범용 에이전트로 활용되고 있어. 그러나 UX가 터미널에 코드 에디터 형태, 환경세팅까지 해야해서 비개발자들에게는 어려워.
그래서 쏘타는 캔버스가 일종의 컨텍스트 공용 공간이 되고 (파일트리) 클로드 코드의 파일을 읽고 검색하는 툴을 제공하고 코딩 에이전트를 따로 제공해서,
1. 나의 업무맥락을 쉽게 메시지 보내듯이 올려놓고 (링크, 첨부파일, 노트 등)
2. 또는 말로 맥락을 쭉 전달하고
3. 이 인풋, 맥락들이 캔버스에 저장되어 있고
4. 이를 바탕으로 쏘타 에이전트가 범용 툴을 사용해서 캔버스에 자료를 읽고 웹검색을 하고 코딩 에이전트를 호출하거나 다른 앱을 호출해서 유저가 원하는 결과물을 만들어내.
그래서 이 완성된 쏘타에서는 클로드 코드라는 키워드를 마케팅적으로 사용할 수 있어. 아까 OPENCLAW 예시처럼.
근데 문제는 아직 그정도까지 개발이 되지 않았다는거지. 현재는 링크, 유튜브, 오디오, PDF 등을 올리면 캔버스에 정리가 되고, AI가 읽을 수 있는 형태로 추출되고, 이를 AI가 읽고 답을 하고 있어. 딱 이정도 기능에서도 문제가 소구되고 사람들이 필요성을 느끼는 문제여야 한다고 생각해서 바로 런칭을 하기로 했고, 이번 마케팅 메시지에서도 클로드 코다 어렵지 않으세요? 가 아니라 복붙 지옥으로 잡은거야.
여기서 내 질문은 이거야,
1. 빠른 배포를 위해 복붙 지옥으로 소구점을 잡았더라도 아직은 기능이 편하거나 와우하지 않아. 캔버스에 직접 링크를 추가해야하거든. 그래서 와우한 포인트를 보여주기 위한 개발이 필요할거 같은데 너 생각은 어때? 어떤 기능들이 있을거 같아? 내가 생각하는거는 모바일 웹에서 바로 녹음이나 메모, 자료를 보낼 수 있게 하는 기능이야.
2. 두번째로 복붙지옥 소구점을 더 강하게 하기 위한 와우포인트 개발(1번의 기능)을 먼저 하는게 좋을까, 아니면 나의 궁극적인 방향인 클로드 코드에 가까워지기 위한 와우 포인트를 개발하는데 리소스를 쓰는게 나을까? (리소스 우선순위 문제) 이쪽 기능은 뭐가 있냐면, 결과물을 빠르게 먼저 보여주는 플로우를 구현하는거야. 자료 올려놓고 말로 ppt 제작 요청. 같은
좋은 질문이고, 지금 판단이 되게 중요해.
결론부터 말하면:

* **지금의 메시지(복붙 지옥)는 맞다**
* 다만 **말만 맞고 체감이 약하면 전환이 안 나온다**
* 그래서 다음 개발은 **“복붙 지옥 해결의 체감 와우”를 먼저** 만드는 게 우선
* 동시에 완전한 Claude Code GUI 쪽으로 가지 말고, **궁극 방향을 보여주는 얇은 결과물 플로우 1개**만 붙이는 게 좋다

즉, **입력 와우 먼저 + 결과물 와우 1개만 얇게**가 가장 좋아 보여.

# 먼저 네 판단 자체에 대한 코멘트

네가 지금 **“클로드 코드 어렵지 않으세요?” 대신 “복붙 지옥”**으로 잡은 건 매우 좋음.

왜냐하면 지금 제품 상태는:

* 범용 에이전트 실행/결과물 생성까지 완성 ❌
* 맥락 수집/정리/AI가 읽기 ✅

즉 **현재 제품이 실제로 잘하는 것과 메시지가 맞아 있음**.
초기엔 이 정합성이 제일 중요해.

문제는 네가 말한 대로:

> 복붙 지옥을 건드리긴 했지만 아직 사용감이 와우하지 않다 (직접 캔버스에 링크 추가해야 함)

이건 정확한 진단이야.

---

# 1) 와우 포인트를 보여주기 위한 개발이 필요한가? → **네, 필요함 (강하게 동의)**

단, **큰 와우 하나**보다 **짧은 시간 안에 느껴지는 와우**가 중요해.

초기 제품에서 와우는 보통 2종류가 있어:

## A. 입력 와우 (Capture wow)

“와 이거 넣는 게 진짜 편하네”

* 습관/재방문을 만듦
* 복붙 지옥 메시지와 직결
* 지금 네 제품 포지셔닝과 가장 잘 맞음

## B. 출력 와우 (Outcome wow)

“와 이걸 이렇게 바로 결과물로?”

* 공유/바이럴에 유리
* 미래 비전(Claude Code GUI)와 연결됨
* 구현 난이도와 품질 리스크가 큼

현재 단계에서는 **A를 먼저 강화**해야 해.
지금은 아직 사용자가 “문제가 해결되는 느낌”을 받기 전에 이탈할 가능성이 크니까.

---

## 네가 제안한 기능: “모바일 웹에서 바로 녹음/메모/자료 보내기”

이거 **매우 좋음**. 거의 정답에 가까움.

왜 좋냐면:

* 복붙 지옥의 본질은 “생각/맥락이 생긴 순간 저장하는 마찰”
* 모바일은 그 마찰이 가장 심한 지점 (회의 중, 이동 중, 링크 봤을 때)
* 여기서 편해지면 사용자가 **‘쏘타를 기본 인박스’처럼 쓰기 시작함**

---

# 1-1) 복붙 지옥 소구를 강하게 만드는 “와우 기능” 후보 (우선순위 포함)

아래는 내가 보기엔 **효율 대비 임팩트** 순서야.

## 1순위: **Quick Capture Inbox (가장 추천)**

핵심 아이디어: 캔버스에 직접 들어가지 않아도 일단 보낼 수 있게

### 형태

* `ssota.ai/inbox` 같은 빠른 입력 페이지
* 링크 붙여넣기 / 파일 첨부 / 텍스트 메모 / 음성녹음
* 보내면 자동으로 캔버스(프로젝트)에 정리됨

### 왜 좋은가

* 캔버스 진입 부담 제거
* “복붙 지옥 해결” 체감이 바로 남
* 구현 난이도도 비교적 현실적

### 와우 포인트 연출

보내자마자 3~10초 내:

* 제목 추출
* 한 줄 요약
* 소스 타입 분류 (유튜브/PDF/문서/오디오)
* 관련 기존 자료 추천(있으면 더 좋음)

> “넣는 순간 정리된다”가 포인트

---

## 2순위: **모바일 공유(Share to SSOTA)**

특히 네가 말한 방향과 완벽하게 맞음.

### 예시 UX

* 유튜브/브라우저/파일앱에서 공유 버튼
* “SSOTA로 보내기”
* 프로젝트 선택 (또는 최근 프로젝트 자동)
* 끝

### 왜 좋은가

* 실제 복붙 행동을 대체함
* 마케팅 문구와 기능의 일치도가 높음
* 사용자에게 “이제 저장 습관이 바뀌네?” 느낌

### 비고

* 플랫폼별 구현 난이도 차이 있음 (앱/확장/PWA 한계 등)
* 그래서 초기에는 **웹 인박스 + 모바일 최적화**로 시작하고, 이후 네이티브/확장으로 가도 됨

---

## 3순위: **브라우저 확장 / 북마클릿 (Send to SSOTA)**

데스크톱 사용자용 복붙 지옥 해결 핵심.

### 기능

* 현재 페이지를 클릭 한 번으로 보내기
* 선택한 텍스트 + URL 같이 저장
* 현재 탭 제목/메타데이터 자동 추출

### 효과

* “자료 수집” 흐름이 압도적으로 편해짐
* 리서치/기획 사용자에게 진짜 꽂힘

---

## 4순위: **음성 메모 원탭 캡처 (모바일)**

회의/이동 중 “생각/업무지시”를 바로 컨텍스트화

### 와우 포인트

* 버튼 누르고 말하면
* 자동 전사 + 요약 + TODO/질문 분리
* 프로젝트 캔버스에 들어감

이건 네 제품 철학과 매우 잘 맞음:

> “말로 맥락을 전달하고, 저장되고, 나중에 에이전트가 활용”

---

## 5순위: **자동 프로젝트 분류 / 추천 라우팅**

보낸 자료를 AI가 알아서 프로젝트 후보 추천

예:

* “이 링크는 [신규 랜딩페이지], [시장조사], [브랜딩] 중 어디에 넣을까요?”
* 또는 자동으로 최근 관련 캔버스에 붙이기

이건 기능 자체보다 **체감 편의**가 크고, “AI 협업공간” 느낌을 확 살려줌.

---

## 보류 추천 (지금은 이르다)

* 자동 클립보드 감시(프라이버시 이슈/거부감 큼)
* 범용 앱 연동 무한 확장
* 고도화된 실시간 화면 추적(기술적 난이도/신뢰 이슈 큼)

초기엔 **단순하고 명확한 캡처 경험**이 더 중요해.

---

# 2) 우선순위: 복붙지옥 와우 vs Claude Code 방향 와우?

## 내 답: **복붙지옥 와우를 먼저**, 단 **Claude Code 방향의 결과물 와우는 얇게 1개만**

이유는 3개야.

---

## 이유 1) 지금 네 메시지와 제품이 정렬된 곳이 “복붙 지옥 해결”

초기엔 유저가 기대한 걸 바로 느끼게 해야 해.

지금 유저가 들어와서 기대하는 건:

* “아 자료 넣는 게 편해졌네”
* “AI가 맥락 읽네”

근데 여기서 바로 “PPT 만들어줘”로 가면,

* 품질 기대치 높아짐
* 실패 확률 올라감
* 제품 정체성이 흐려질 수 있음 (또 하나의 제너레이터처럼 보임)

---

## 이유 2) 입력 마찰이 크면, 결과물 와우도 못 봄

아무리 결과물 생성이 좋아도,
사용자가 자료 올리는 과정에서 귀찮으면 거기까지 안 감.

즉 **입력 퍼널이 막히면 출력 와우는 의미가 없음**.

---

## 이유 3) 하지만 결과물 와우가 전혀 없으면 “그냥 요약툴”로 보일 수 있음

여기가 핵심 포인트.

그래서 나는 이렇게 추천:

* **메인 개발 리소스는 입력 와우**
* **서브 리소스로 결과물 와우 1개만** (템플릿 기반, 좁은 범위)

---

# 추천 전략: 70 / 20 / 10 리소스 배분

## 70% — 복붙 지옥 해결 체감 강화 (지금 약속 강화)

예:

* Quick Capture Inbox
* 모바일 음성/메모/링크 캡처
* 브라우저 send-to-SSOTA
* 자동 정리/분류/요약

## 20% — 결과물 와우 1개 (미래 비전 데모)

예:

* “자료 올리고 한 문장 말하면 **PPT 초안 아웃라인** 생성”
* “리서치 브리프/PRD 초안 생성”
* “회의록 → 실행계획 문서”

> 여기서 중요한 건 “범용 에이전트 완성”이 아니라
> **한 가지 결과물 플로우를 매끈하게** 만드는 것

## 10% — Claude Code GUI 방향의 기반 설계

예:

* 툴 호출 로그/추적 UI 기초
* 작업 단계 표시 (계획→수집→작성)
* 캔버스 내 실행 trace 구조

이건 미래 방향의 씨앗으로만.

# “Claude Code에 가까워지는 와우”를 지금 한다면, 뭐가 최소단위로 좋나?

네가 예시로 든:

> 자료 올려놓고 말로 PPT 제작 요청

좋은 방향인데, 그대로 가면 범위가 커질 수 있어.
그래서 **“PPT 완성”보다 “PPT 초안 생성”**으로 잘라서 시작하는 걸 추천.

## 추천 최소단위 결과물 와우 (MVP)

### 1) 소스 → 발표 초안 아웃라인

* 입력: 링크/PDF/오디오
* 요청: “이걸 바탕으로 10장 발표 구성”
* 출력:

  * 슬라이드 제목 리스트
  * 각 슬라이드 핵심 bullet
  * 근거 소스 참조
  * 발표 목적별 톤(투자자/사내공유/영업제안)

이건 네 현재 capability와도 연결됨 (이미 읽고 답할 수 있으니까).

### 2) 소스 → 업무 실행 브리프

* 입력: 회의녹음 + PDF + 링크
* 요청: “다음 주 실행계획 만들어줘”
* 출력:

  * 요약
  * 결정사항
  * 미결 질문
  * 담당자/기한 (placeholder)
  * 다음 액션

이건 “일잘러 협업공간” 포지션과 더 잘 맞음.

### 3) 소스 → 카드뉴스/상세페이지 초안 구조

(네가 잘할 수 있는 영역)

* 섹션 구조
* 메시지 흐름
* 카피 초안
* 필요한 비주얼 리스트

# 내가 추천하는 실제 실행 순서 (현실적인 2스텝)

## Step 1 (지금): 복붙 지옥 체감 해결

**목표:** “넣는 게 편하다”를 느끼게

### 꼭 넣으면 좋은 것 (핵심 2개)

1. **Quick Capture Inbox (링크/파일/텍스트/음성)**
2. **모바일 우선 캡처 UX** (적어도 웹에서 빠르게)

추가로 가능하면:

* 전송 후 자동 요약 카드
* 최근 프로젝트 추천

### 마케팅 문구도 강화됨

* “복붙 말고 그냥 보내세요”
* “보내면 자동으로 정리되고 AI가 이해합니다”

---

## Step 2 (바로 다음): 결과물 와우 1개

기능 요약  
/inbox 페이지에 채팅창이 있음  
현재 올라가는 소스 데이터는 blocks 데이터 모델로 저장됨. Blocks는 워크스페이스 기준. Blocks는 여러 개의 페이지 (캔버스)애 올라갈 수 있음. 이게 블록 마운트.  
Blocks는 일종의 구글 드라이브 같은 느낌으로 모든 유니크한 소스를 의미  
채팅창 형태인데 일반 ai채팅은 아님. 범용적이지 않고 룰베이스 느낌.   
아무것도 없는 채팅창에 인풋 넣기 누르면, 소스 종류를 클릭하고 인풋으로 넣기 가능. 파일, 오디오, 메모 형태에 맞게 빠르게 올리기  
올라가면 채팅 버블로 올라감.  
그러면 db 관점에서는 blocks에 등록되서 추출 요약 진행됨. 그리고 결과를 채팅 버블로 볼 수 있음. 카드 형태로 나오고, 클릭하면 바텀시트로 결과 디테일하게 볼 수 있음.  
그리고 어차피 이미 요약되어 있기 때문에 내용은 알고 있음. 이를 기반으로 Llm에게 해당 소스의 요약 내용과 유저가 보유한 페이지를 컨텍스트로 제공해서 블록이 배치될 추천 페이지를 뽑도록 하기. 그 추천 페이지는 배지 형태로 선택할 수 있도록 하고, 선택하면 페이지 캔버스에 저장됨. 물론 모바일에서 보기는 어려움. 아니면 처음부터 페이지를 선택할 수 있음.  
특히 올리는 것들은 진짜 채팅은 아니지만, 채팅을 새로 파는 느낌으로 올리면서 같은 채팅에 올리는 경우는 같은 맥락으로 판단하기(?) (그냥 아이디어)  
그냥 /chat 페이지도 있어서 편하게 대화하면서 기존에 올려놓은 소스 읽어오도록 하거나, 웹검색을 하거나 하면서 대화가능. 대화 결과를 또 바로 노트형식이든 다른 형태로 블록 저장 가능. 그렇게 소스가 계속 쌓여가는 형태.  
  여기까지 기능 아이디에이션을 정리해줘.

그리고 이거는 딴 얘기인데 10%인지 20%인지 어디에 해당되는지는 모르겠지만, 특정 업무를 수행하는 클로드 스킬처럼 우리도 스킬을 지정하고 나눌 수 있는 공간이 있어.  
그리고 이를 특화시킨 서브에이전트 개념도 있고, 서브에이전트가 다룰 수 있는 쏘타 앱도 있어. 쏘타 앱은 에이전트가 직접 조작하기 쉽게 tool adapter를 제공하고 사람이 읽기도 쉬운 (현재 앱 ux) 형태로 구성되어 쏘타 위에서 구동되는 앱임. 이거는 어디에 들어가고 어느 시점에 어떤 순서로 개발되는게 좋을까좋다. 이거 지금 꽤 잘 정리돼 있고, **쏘타의 “현재 가능한 것”과 “미래 방향”이 같은 선 위에 있음**.

# 1) 기능 아이디에이션 정리 (현재 구상)

## A. 핵심 개념 모델

### 1) Workspace

* 사용자의 작업 공간 단위
* 모든 `Blocks`의 소유 범위 기준

### 2) Block (유니크 소스)

* 쏘타의 핵심 데이터 모델
* 파일 / 링크 / 오디오 / 메모 / 대화 결과 노트 등 **모든 유니크 소스**
* 구글 드라이브의 “파일” 같은 역할
* 한 번 생성되면 여러 페이지(캔버스)에 재사용 가능

### 3) Page (Canvas)

* 작업 맥락/결과물을 구성하는 공간
* 하나의 Page에 여러 Block이 배치될 수 있음

### 4) Block Mount

* 하나의 Block이 여러 Page에 올라가는 구조
* Block은 유니크하게 저장되고, Page에는 “마운트”됨 (참조/배치)

> 이 구조가 아주 좋음.
> “수집(소스)”과 “구성(캔버스)”이 분리되어 있어서 확장성 높음.

---

## B. `/inbox` 페이지 (빠른 입력 중심, 채팅형 UI)

### 목적

* 일반 AI 채팅이 아니라, **소스 수집/정리/라우팅을 위한 입력 허브**
* 사용자가 “메시지 보내듯” 빠르게 업무 맥락을 넣는 공간

### UI 성격

* 채팅창처럼 보이지만 범용 채팅 아님
* **룰베이스형 입력/처리 플로우** 중심
* 입력된 항목이 채팅 버블처럼 쌓임 (심리적으로 익숙한 인터페이스)

### 입력 방식

* 빈 채팅창에서 `인풋 넣기` 버튼
* 소스 종류 선택 후 빠르게 업로드

  * 파일
  * 오디오
  * 메모 (텍스트)
  * (추가 가능: 링크/유튜브 URL)

### 업로드 후 동작

* 채팅 버블로 업로드 상태 표시
* DB에는 `Blocks`로 등록
* 비동기 처리:

  * 추출 (텍스트/메타데이터)
  * 요약 생성
  * (옵션) 태깅/분류
* 처리 결과를 채팅 버블 내 카드 형태로 표시
* 카드 클릭 시 바텀시트에서 상세 결과 확인

### 바텀시트 상세 예시

* 원문 메타데이터 (제목/소스 타입/길이)
* 추출 텍스트 일부/전체
* 요약
* 핵심 포인트
* (향후) 액션 아이템/질문/태그

---

## C. 페이지(캔버스) 배치 추천 플로우

### 배경

* 이미 요약/추출된 상태이므로, LLM이 내용을 어느 정도 파악 가능
* 사용자의 기존 Page(캔버스) 맥락과 매칭 가능

### 추천 로직 구상

LLM에 제공:

* 해당 소스(Block)의 요약 내용
* 사용자 보유 Page 목록 (제목/설명/최근 블록/태그 등 메타)
* (옵션) 현재 inbox 세션 맥락

LLM 출력:

* 추천 Page 후보 n개
* 추천 이유(짧게)
* 확신도/우선순위

### UX

* 추천 Page를 **배지(chip)** 형태로 보여줌
* 사용자가 선택하면 해당 Page에 Block mount 저장
* 또는 처음부터 업로드 전/후에 Page를 직접 선택 가능

### 모바일 고려

* 모바일에서 캔버스 자체 보기 어렵다면,

  * “캔버스에 배치” 대신
  * “Page에 저장됨” 상태만 보여주고
  * 데스크톱에서 구조 확인하게 유도

> 이 방향 좋음. 모바일은 “수집/분류”, 데스크톱은 “구성/편집” 역할 분리 가능.

---

## D. Inbox 내 “맥락 세션” 개념 (아이디어 단계)

### 아이디어

* 같은 inbox 채팅 흐름(같은 스레드/세션)에 올린 인풋들은

  * 같은 주제/업무 맥락으로 간주할 수 있음

### 활용 가능성

* 요약 시 맥락 반영
* 페이지 추천 정확도 향상
* 이후 `/chat`에서 “방금 올린 것들 기반으로…” 같은 요청 가능

### 주의점 (초기)

* 자동으로 너무 강하게 묶으면 오분류 가능
* 초기에는 **“같은 세션 = 약한 힌트”** 정도가 안전

  * 자동 확정 X
  * 추천 가중치 O

---

## E. `/chat` 페이지 (범용 대화 + 소스 활용)

### 목적

* 보다 일반적인 대화형 인터페이스
* 기존에 축적된 소스를 읽어오고, 웹검색하고, 작업을 진행하는 공간

### 가능한 동작

* 기존 Block(소스) 참조해서 대화
* 웹검색 수행
* (향후) 스킬/서브에이전트 호출
* 결과를 다시 Block으로 저장

  * 노트
  * 요약
  * 초안
  * 계획 문서 등

### 핵심 가치

* `/inbox`가 “수집”
* `/chat`이 “활용/생성”
* 결과가 다시 Block으로 저장되어 지식 자산이 계속 누적됨

> 이 순환 구조가 SSOTA의 강점임:
> **수집 → 이해 → 대화/작업 → 결과물 저장 → 재활용**

# 3) 지금 구상에서 특히 좋은 포인트 (강점)

## 1) 데이터 모델이 먼저 잘 잡혀 있음

## 2) `/inbox`와 `/chat` 역할이 다름

* 둘을 분리하면 UX가 명확해짐

## 3) 결과를 다시 Block으로 저장하는 순환 구조

* 이게 진짜 중요함
* 그냥 챗봇이 아니라 **지식/업무 자산이 쌓이는 시스템**이 됨

# 4) 구현 전에 결정하면 좋은 것들 (짧은 체크리스트)

## A. `/inbox`는 “세션(thread)” 개념을 가질지?

추천: **가져가는 게 좋음**

* `inbox_sessions` 같은 개념
* 같은 세션의 입력들은 약한 맥락 공유
* 나중에 “이번 회의 관련 자료”처럼 묶기 쉬움

## B. Page 추천은 자동 마운트 vs 사용자 선택?

추천: **초기엔 추천 + 사용자 선택**

* 자동 마운트는 실수 비용 큼
* 추천 배지 클릭 UX가 안전하고도 똑똑해 보임

## C. 요약 완료 전에도 저장할지?

추천: **즉시 Block 생성 + 처리상태 표시**

* 업로드 즉시 성공감 제공
* 추출/요약은 async로 진행
* 상태 배지: `업로드됨 / 추출중 / 요약완료 / 실패`

## D. `/chat`에서 소스 참조 방식

초기 추천:

* 명시적 선택(칩/멘션) + 자동 추천 혼합
* 완전 자동은 예측 불가 느낌 줄 수 있음

이건 아주 좋은 질문이고, 답은 이거야:

## 결론

* **스킬(Skills)**: 비교적 빨리 사용자에게 보일 수 있는 계층 (20%에 넣기 좋음)
* **서브에이전트(Subagents)**: 당장은 내부 orchestration 중심 (10% 기반 성격)
* **쏘타 앱(SSOTA Apps + tool adapter)**: 장기적으로 매우 중요하지만 초기에 크게 열면 무거움 (10% 기반 + 이후 확장)

즉,

* 사용자 와우로 바로 쓰기 좋은 건 **스킬**
* 미래 플랫폼 파워의 핵심은 **서브에이전트 + 쏘타 앱**

---

## 개념 계층으로 보면 이렇게 정리됨

### 1) Skills (사용자-facing 작업 템플릿/능력)

* “이런 업무를 해주는 기능 묶음”
* 예: 회의록 정리, 발표 아웃라인 생성, 경쟁사 비교표 초안, 카드뉴스 구조 짜기
* Claude Skills처럼 **특정 업무 수행 방식**을 선택하는 단위

**위치**

* `/chat`에서 호출하기 좋음
* `/inbox` 처리 후 “다음 액션 제안”으로도 연결 가능

**현재 단계에서의 역할**

* 사용자에게 결과물 와우를 보여주는 가장 쉬운 수단

---

### 2) Subagents (오케스트레이션 실행 단위)

* 특정 역할에 특화된 에이전트
* 자신만의 지시/툴 접근 권한/앱 접근 범위를 가질 수 있음
* 예: 리서치 에이전트, 문서 구조화 에이전트, 디자인 브리프 에이전트

**위치**

* 초기에는 사용자에게 직접 노출하지 않아도 됨
* 내부적으로 스킬 실행 엔진처럼 사용 가능

**현재 단계에서의 역할**

* “스킬의 구현체”로 숨겨두기 좋음
  (사용자에게는 스킬만 보이고, 내부에선 서브에이전트가 실행)

---

### 3) SSOTA Apps (에이전트가 조작 가능한 앱 런타임)

* 쏘타 위에서 구동되는 앱
* tool adapter 제공 → 에이전트가 직접 조작 가능
* 사람에게도 읽기 쉬운 UI 제공

예시 상상:

* 아웃라인 앱
* 테이블/비교 앱
* 타임라인 앱
* 슬라이드 초안 앱
* 리서치 보드 앱

**위치**

* 장기적으로 “Claude Code GUI” 방향의 핵심
* 단기에는 1~2개 first-party 앱으로 시작하는 게 좋음

---

# 6) 이 3개(스킬/서브에이전트/앱)의 개발 시점과 순서 추천

## 내가 추천하는 순서 (중요)

### Phase 1 — 내부 스킬화 (지금~가까운 시점)

**목표:** 현재 기능을 구조화하고 재사용 가능하게 만들기

#### 할 일

* 지금 있는 처리 로직(요약/추출/페이지추천)을 “스킬”처럼 내부 모듈화
* 사용자에겐 숨겨도 됨
* 예:

  * `extract_source`
  * `summarize_source`
  * `recommend_pages`
  * `save_as_block`

**왜 먼저?**

* 이후 `/chat`, `/inbox`, 서브에이전트 어디서든 재사용 가능
* 제품이 빨라짐 + 안정화됨

> 이건 10% 기반에 가깝지만, 당장 체감 개선에도 기여해서 매우 가치 있음.

---

### Phase 2 — 사용자-visible Skills (가장 추천되는 다음 단계)

**목표:** 결과물 와우를 빠르게 보여주기

#### 예시 스킬 3개만 공개

* `회의록 → 실행계획`
* `소스 묶음 → 발표 아웃라인`
* `자료 → 요약 노트 블록 저장`

#### UX

* `/chat`에서 스킬 선택
* 또는 `/inbox` 카드 아래 “다음으로 하기” 버튼으로 제안

**왜 이 단계가 좋나?**

* Claude Code류의 “작업 단위 실행” 느낌을 전달 가능
* 서브에이전트/앱을 아직 크게 노출 안 해도 됨

> 이건 20% (결과물 와우) 쪽에 아주 잘 맞음.

---

### Phase 3 — Subagent 개념 도입 (초기엔 반노출/고급모드)

**목표:** 복잡한 작업 흐름을 분리 실행 가능하게

#### 방법

* 처음엔 사용자에게 “서브에이전트” 용어를 강하게 노출하지 말고
* 내부적으로만:

  * Research agent
  * Structuring agent
  * Writer agent
* 실행 trace만 간단히 보여주기

  * “조사 중 → 정리 중 → 초안 작성 중”

**왜 이 순서?**

* 사용자 입장에선 결과가 먼저 중요
* 서브에이전트는 결과 품질/확장성을 위해 필요하지만, 너무 일찍 노출하면 복잡해 보임

> 이건 명확히 10% 기반/미래 방향 축.

---

### Phase 4 — SSOTA Apps (1개씩, first-party 중심)

**목표:** 에이전트가 조작 가능한 구조화된 결과물 공간 확보

#### 추천 시작점

* “슬라이드 완성 앱”보다 먼저
* **아웃라인/브리프 앱** 같은 구조화 UI부터

예:

1. **Outline App**

   * 섹션/슬라이드/논리흐름 관리
   * 에이전트가 항목 추가/수정 쉬움
2. **Research Board App**

   * 근거/요약/인사이트 카드 구조화
3. **Action Plan App**

   * 결정사항/할 일/질문 관리

**왜?**

* PPT/디자인/영상 완성 툴은 난이도 높고 기대치 높음
* 구조화 앱은 네 현재 강점(맥락/요약/정리)과 딱 맞음
* 에이전트 조작하기도 쉬움 (tool adapter 설계 간단)

# 7) 이걸 70/20/10에 매핑하면

## 70% (지금 메인)

**복붙 지옥 해결 체감**

* `/inbox` 빠른 입력 UX
* 모바일 입력(녹음/메모/파일/링크)
* 업로드 후 즉시 요약 카드/바텀시트
* 페이지 추천 배지 + 마운트

## 20% (가까운 와우)

**사용자-visible Skills**

* 자료 기반 결과물 초안 생성
* `/chat`에서 스킬 실행
* 결과를 블록으로 저장

## 10% (미래 기반)

**Subagent + SSOTA Apps 기반 구조**

* 내부 오케스트레이션
* tool adapter 규약
* 실행 trace 구조
* 첫 앱의 최소 스키마/런타임

# 8) 실무적으로 가장 좋은 개발 순서 (현실 버전)

## 1단계: `/inbox` 완성도 올리기 (우선)

* 입력 타입 빠른 업로드
* 처리 상태/결과 카드
* 바텀시트 상세
* 추천 페이지 배지 + 마운트
* (선택) inbox session 개념

## 2단계: `/chat`에서 “블록 저장되는 결과물” 만들기

* 그냥 대화가 아니라 결과가 자산화되는 경험
* 노트 블록 저장 / 요약 블록 저장 / 실행계획 블록 저장

## 3단계: 스킬 2~3개 공개

* 버튼/메뉴 기반으로 호출
* 결과 품질 안정적인 것부터

## 4단계: 내부 서브에이전트화

* 스킬 실행 내부 구현 분리
* 나중에 사용자-facing trace로 확장

## 5단계: 첫 SSOTA App (아웃라인/브리프형)

* 에이전트 조작 가능 + 사람도 읽기 쉬움
* 여기서부터 Claude Code GUI 방향성이 확 보임

# 9) 내가 추가로 추천하는 포인트 (중요)

## “스킬”은 처음부터 사용자에게 많이 보여주지 말기

초기엔 스킬이 많아지면 오히려 복잡해짐.

* 2~3개만
* 이름도 업무 중심으로

  * “발표 구성 만들기”
  * “회의 액션 정리”
  * “자료 요약 노트 만들기”

## “서브에이전트”는 내부 용어로 먼저 쓰기

사용자에게는 당장 “스킬”이 더 직관적임.

* 나중에 고급 사용자용으로 “에이전트 팀” UI 열기

## “앱”은 결과물 완성툴보다 구조화툴부터

이게 SSOTA에 더 맞고, 빠르게 성공 가능성 높음.
