# /inbox 기능 기획 문서

> 본 문서는 `inbox.plan.md` 대화 내용을 기반으로 정리한 /inbox 기능 상세 기획입니다.
> Quick Capture Inbox 구현을 위한 핵심 스펙을 담고 있습니다.

**Event Storming 문서**: [`docs/event-domain-design/domains/inbox-management-domain/01-event-storm.md`](../event-domain-design/domains/inbox-management-domain/01-event-storm.md)

---

## 1. 문서 개요

### 1.1 목적

- `/inbox` 페이지의 목적, UI/UX, 데이터 모델, 플로우를 정의
- "복붙 지옥 해결" 소구의 핵심 체감 와우를 구현하기 위한 기획

### 1.2 제품 정의 (한 줄)

> 쏘타는 "채팅처럼 쉽게 업무 맥락을 수집(/inbox)하고, 캔버스에 구조화(Page/Block Mount)하며, AI 대화와 작업(/chat) 결과까지 다시 소스로 축적하는 시스템"이다.

---

## 2. 핵심 개념 모델

### 2.1 Workspace

- 사용자의 작업 공간 단위
- 모든 `Blocks`의 소유 범위 기준

### 2.2 Block (유니크 소스)

- 쏘타의 핵심 데이터 모델
- 파일 / 링크 / 오디오 / 메모 / 대화 결과 노트 등 **모든 유니크 소스**
- 구글 드라이브의 "파일" 역할
- 한 번 생성되면 여러 페이지(캔버스)에 재사용 가능

### 2.3 Page (Canvas)

- 작업 맥락/결과물을 구성하는 공간
- 하나의 Page에 여러 Block이 배치될 수 있음

### 2.4 Block Mount

- 하나의 Block이 여러 Page에 올라가는 구조
- Block은 유니크하게 저장되고, Page에는 "마운트"됨 (참조/배치)
- "수집(소스)"과 "구성(캔버스)"이 분리된 구조 → 확장성 높음

---

## 3. /inbox 페이지 개요

### 3.1 목적

- 일반 AI 채팅이 아닌 **소스 수집/정리/라우팅을 위한 입력 허브**
- 사용자가 "메시지 보내듯" 빠르게 업무 맥락을 넣는 공간

### 3.2 UI 성격

| 항목 | 설명 |
|------|------|
| 외관 | 채팅창처럼 보이지만 범용 채팅 아님 |
| 성격 | **룰베이스형 입력/처리 플로우** 중심 |
| 피드백 | 입력된 항목이 채팅 버블처럼 쌓임 (심리적으로 익숙한 인터페이스) |

### 3.3 /inbox vs /chat 역할 분리

| 페이지 | 역할 |
|--------|------|
| `/inbox` | 수집 (Capture) — 빠른 입력, 정리, 라우팅 |
| `/chat` | 활용/생성 — 대화, 웹검색, 결과물 생성, Block 저장 |

결과가 다시 Block으로 저장되어 지식 자산이 계속 누적되는 **순환 구조**가 핵심 가치.

---

## 4. 입력 플로우

### 4.1 입력 방식

1. 빈 채팅창에서 **"인풋 넣기"** 버튼 클릭
2. 소스 종류 선택 후 빠르게 업로드

| 소스 타입 | 설명 |
|-----------|------|
| 파일 | PDF, 문서 등 |
| 오디오 | 음성 녹음 |
| 메모 | 텍스트 |
| 링크 | URL 붙여넣기 |
| 유튜브 | URL 입력 |

### 4.2 업로드 후 동작

1. **채팅 버블**로 업로드 상태 표시
2. DB에 **Blocks**로 등록
3. 비동기 처리:
   - 추출 (텍스트/메타데이터)
   - 요약 생성
   - (옵션) 태깅/분류
4. 처리 결과를 **채팅 버블 내 카드 형태**로 표시
5. 카드 클릭 시 **바텀시트**에서 상세 결과 확인

### 4.3 처리 상태

| 상태 | 설명 |
|------|------|
| `업로드됨` | Block 생성 완료, 처리 대기 |
| `추출중` | 텍스트/메타데이터 추출 중 |
| `요약완료` | 요약/정리 완료 |
| `실패` | 처리 실패 |

> **추천:** 즉시 Block 생성 + 처리상태 표시 (업로드 즉시 성공감 제공)

---

## 5. 바텀시트 상세 UI

카드 클릭 시 바텀시트에서 표시할 정보:

- 원문 메타데이터 (제목/소스 타입/길이)
- 추출 텍스트 (일부/전체)
- 요약
- 핵심 포인트
- (향후) 액션 아이템, 질문, 태그

---

## 6. 페이지(캔버스) 배치 추천 플로우

### 6.1 배경

- 이미 요약/추출된 상태이므로 LLM이 내용 파악 가능
- 사용자의 기존 Page 맥락과 매칭 가능

### 6.2 추천 로직

**LLM에 제공하는 입력:**
- 해당 소스(Block)의 요약 내용
- 사용자 보유 Page 목록 (제목/설명/최근 블록/태그 등 메타)
- (옵션) 현재 inbox 세션 맥락

**LLM 출력:**
- 추천 Page 후보 n개
- 추천 이유(짧게)
- 확신도/우선순위

### 6.3 UX

- 추천 Page를 **배지(chip)** 형태로 표시
- 사용자가 **선택**하면 해당 Page에 Block mount 저장
- 또는 **처음부터** 업로드 전/후에 Page를 직접 선택 가능

> **추천:** 초기엔 **추천 + 사용자 선택** (자동 마운트는 실수 비용이 큼)

### 6.4 모바일 고려

- 모바일에서 캔버스 전체 보기 어려운 경우:
  - "캔버스에 배치" 대신 "Page에 저장됨" 상태만 표시
  - 데스크톱에서 구조 확인 유도
- 역할 분리: 모바일 = 수집/분류, 데스크톱 = 구성/편집

## 7. Inbox 세션 개념 (아이디어)

### 7.1 개념

- 같은 inbox 채팅 흐름(같은 스레드/세션)에 올린 인풋들은 **같은 주제/업무 맥락**으로 간주 가능

### 7.2 활용 가능성

- 요약 시 맥락 반영
- 페이지 추천 정확도 향상
- `/chat`에서 "방금 올린 것들 기반으로…" 같은 요청 가능

### 7.3 초기 구현 권장사항

- 자동으로 너무 강하게 묶으면 오분류 위험
- 초기에는 **"같은 세션 = 약한 힌트"** 수준
  - 자동 확정 X
  - 추천 가중치 O

> **결정 사항:** `inbox_sessions` 같은 개념 도입, 같은 세션의 입력은 약한 맥락 공유

## 8. 와우 포인트 연출 (Quick Capture Inbox)

보내자마자 **3~10초 내** 표시:

- 제목 추출
- 한 줄 요약
- 소스 타입 분류 (유튜브/PDF/문서/오디오)
- 관련 기존 자료 추천 (있으면 더 좋음)

> **핵심 메시지:** "넣는 순간 정리된다"

## 9. 구현 전 결정 사항 체크리스트

### A. /inbox는 "세션(thread)" 개념을 가질지?

- **추천:** 가져가는 것이 좋음
- `inbox_sessions` 개념
- 같은 세션의 입력들은 약한 맥락 공유
- "이번 회의 관련 자료"처럼 묶기 용이

### B. Page 추천은 자동 마운트 vs 사용자 선택?

- **추천:** 초기엔 **추천 + 사용자 선택**
- 자동 마운트는 실수 비용 큼
- 추천 배지 클릭 UX가 안전하면서 똑똑해 보임

### C. 요약 완료 전에도 저장할지?

- **추천:** 즉시 Block 생성 + 처리상태 표시
- 업로드 즉시 성공감 제공
- 추출/요약은 async 진행

### D. /chat에서 소스 참조 방식

- **추천:** 명시적 선택(칩/멘션) + 자동 추천 혼합
- 완전 자동은 예측 불가 느낌을 줄 수 있음

## 10. 기능 플로우 요약

```
[인풋 넣기] → [소스 선택] → [업로드] → [Block 생성]
                                    ↓
                    [추출] → [요약] → [카드 표시]
                                    ↓
                    [바텀시트 상세] ← [카드 클릭]
                                    ↓
                    [LLM 페이지 추천] → [배지 표시]
                                    ↓
                    [사용자 선택] → [Block Mount → Page]
```

## 11. Event Storming 기반 이벤트 흐름

Event Storming 결과, **Inbox Management 도메인 내부** 이벤트만 정의합니다 (백엔드 관점).  
프론트엔드·다른 도메인·호출 요청 이벤트는 제외하며, 소스 검증/추출/요약은 Source 도메인 이벤트로 별도 정의합니다.

### Inbox 도메인 이벤트 (6개)

| 카테고리 | 이벤트 |
|----------|--------|
| 세션·메시지 | Inbox Session Created, Inbox Message Added, Inbox Message Deleted |
| 페이지 추천 결과 | Page Recommendations Generated by LLM |
| 처리 실패·재시도 | Inbox Message Processing Failed, Inbox Message Processing Retry Initiated |

### Command-Event 대응

- **Inbox Processing Retry Requested** (Command) → **Inbox Message Processing Retry Initiated** (Event)
- 처리 실패: **Inbox Message Processing Failed** ([작업] Failed 패턴, 다른 도메인과 동일)

상세 정의 및 Commands & Actors는 [Inbox Management Domain Event Storm](../event-domain-design/domains/inbox-management-domain/01-event-storm.md) 문서를 참조하세요.

## 12. 데이터 모델 초안 (참고)

구현 시 참고할 주요 엔티티:

- `blocks` — 유니크 소스
- `pages` — 캔버스/페이지
- `page_block_mounts` — Block과 Page 연결
- `inbox_sessions` — inbox 세션
- `inbox_messages` — inbox 내 메시지(입력) 단위
- `block_derivatives` — 추출/요약 결과 (필요 시)

## 13. 개발 순서 (실무 버전)

### 1단계: /inbox 완성도 올리기 (우선)

- [ ] 입력 타입별 빠른 업로드
- [ ] 처리 상태/결과 카드
- [ ] 바텀시트 상세
- [ ] 추천 페이지 배지 + 마운트
- [ ] (선택) inbox session 개념

### 2단계: 모바일 최적화

- [ ] 모바일 웹 최적화
- [ ] 음성 녹음 / 메모 입력
- [ ] Share to SSOTA (가능 시)

### 3단계: /chat 연동

- [ ] /chat에서 블록 저장되는 결과물
- [ ] 노트/요약/실행계획 Block 저장

## 14. 참고: 전체 제품 구조

```
/inbox (수집) ──→ Blocks ──→ Pages (캔버스)
    ↑                              ↓
    └──── /chat (활용/생성) ←──────┘
              (결과를 Block으로 저장)
```

**순환 구조:** 수집 → 이해 → 대화/작업 → 결과물 저장 → 재활용
