# 모듈 경계 강제 가이드: 논리적 약속 vs 물리적 강제

## 개요

모듈화가 "논리적 약속"으로만 존재할 때, 테스트는 통과해도 **예상하지 못한 의존성**에서 장애가 터지는 경우가 많다. 이 문서는 SSOTA 프로젝트의 현재 모듈화 방식(논리적 경계)을 명확히 하고, **컴파일 타임에 경계를 강제하는 방식**(물리적 경계)과 비교해, 나중에 경계 강제를 강화할 때 참고할 수 있도록 정리한다.

**관련 문서**
- [Server-Side DDD Conventions](./backend/server-side-ddd-conventions.md) — 도메인 레이어와 데이터 흐름
- [Dependency-based Type Layering](./frontend/dependency-based-type-layering.md) — 타입 의존성 순서

## 1. 논리적 경계 vs 물리적 경계

### 1.1 논리적 경계 (Logical Boundaries)

- **정의**: 폴더 구조·네이밍·컨벤션으로 "이렇게 쓰자"라고만 정해둔 경계.
- **특징**:
  - 같은 빌드 단위(예: 하나의 Next.js 앱) 안에 모든 도메인이 있음.
  - 도메인 A에서 도메인 B 내부를 import 해도 **컴파일러는 막지 않음**.
  - 위반 여부는 **코드 리뷰, 린트 규칙, 테스트**에 의존.

**SSOTA의 현재 상태**: `apps/web/src/domains/` 아래 도메인 디렉토리로 구분하고, cross-domain은 `@/domains/[domain]/...` 절대 경로로 import. 규칙 위반 시 **컴파일은 성공**하고, ESLint/리뷰에서만 걸러질 수 있다.

### 1.2 물리적 경계 (Physical Boundaries)

- **정의**: 빌드 시스템(예: Gradle 멀티모듈, npm/pnpm 워크스페이스 패키지)이 **모듈 단위**를 나누고, 의존성은 명시적 선언으로만 허용하는 경계.
- **특징**:
  - 모듈 간 의존성은 `build.gradle` / `package.json`의 `dependencies`에만 존재.
  - 선언되지 않은 모듈을 import 하면 **컴파일(빌드) 에러**.
  - 순환 참조 시 **빌드 실패**로 즉시 감지.

참고: flex팀은 24개 도메인·253개 모듈을 Gradle 멀티모듈 + Hexagonal 아키텍처로 운영하며, Spring Modulith 같은 런타임 검증이 아니라 **컴파일 타임에 경계를 강제**하는 방식을 선택했다.

## 2. SSOTA vs Gradle 기반 물리적 분리 (개념 비교)

### 2.1 모듈화 경계 강제 방식

| 관점 | Gradle 멀티모듈 (물리적) | SSOTA 현재 (논리적) |
|------|---------------------------|----------------------|
| 경계 단위 | 모듈 = 별도 Gradle 프로젝트 | 도메인 = 디렉토리 (`domains/...`) |
| 위반 시 | **컴파일/빌드 실패** | 컴파일 성공, 린트/리뷰에서만 발견 가능 |
| 순환 참조 | 빌드 실패로 **원천 차단** | 런타임/순환 import 시 문제 가능 |
| 의존성 선언 | `dependencies { implementation project(':other-module') }` | 없음 (import 경로 컨벤션만 존재) |

### 2.2 Hexagonal 아키텍처에서의 차이

**공통점**: 둘 다 Port/Adapter, Domain Core 분리를 목표로 한다.

**차이**:

- **물리적 분리**: Domain 모듈은 Infrastructure 모듈을 **빌드 설정상 참조하지 않음**. Domain 코드에서 DB/외부 라이브러리를 import 하면 빌드 에러.
- **SSOTA**: `shared/`(Domain Core)와 `backend/repositories/implementations/`(Adapter)가 같은 앱 안에 있어, 실수로 Domain에서 Drizzle 구현체를 직접 import 해도 **컴파일러가 막지 않음**. 의존성 방향은 컨벤션과 리뷰로만 유지.

### 2.3 순환 의존성

- **Gradle**: 모듈 의존성 그래프가 DAG가 아니면 빌드 실패.
- **SSOTA**: TypeScript는 순환 참조 시 런타임에 `undefined` 등으로 터질 수 있으나, **컴파일은 통과**하는 경우가 많음. `import/no-cycle` 등 린트로 보완 가능하지만 "테스트/정적 분석" 단계의 검증이다.

### 2.4 AI Agent와의 관계

- **물리적 경계**: Agent가 허용된 모듈 외부를 참조하는 코드를 생성하면 **빌드가 실패**해, 즉시 수정 대상이 드러남.
- **논리적 경계만 있을 때**: Agent가 도메인 경계를 넘는 import를 만들어도 빌드는 성공할 수 있어, **도구 설계·프롬프트·리뷰**에 더 의존하게 된다.

## 3. SSOTA의 현재 모듈 구조 요약

- **도메인 구조**: `apps/web/src/domains/[domain]/` 아래  
  `actions/`, `backend/`, `shared/`, `frontend/` 등 레이어별 디렉토리.
- **의존성 규칙** (컨벤션):
  - 같은 도메인: 상대 경로.
  - 다른 도메인: `@/domains/[domain]/...` 절대 경로.
  - Domain Core(`shared/`)는 외부 프레임워크/인프라에 의존하지 않는다 (Hexagonal).
- **강제 수단**: 컴파일러가 아닌 **코드 리뷰·ESLint·문서(본 가이드)**.

이 구조는 **"논리적 약속"** 단계에 해당하며, DDD·Hexagonal 패턴은 잘 적용되어 있으나 **경계 위반을 물리적으로 막는 메커니즘은 없다**.

---

## 4. 논리적 경계의 한계 (왜 "테스트만으로는 부족한가")

- 테스트는 **의도한 시나리오**만 검증한다. "A 도메인이 B 도메인 내부를 직접 참조하지 말자"는 규칙은 테스트만으로는 **완전히** 검증하기 어렵다.
- 새 코드·리팩터링·AI 생성 코드에서 잘못된 의존성이 들어가도 **빌드는 성공**할 수 있어, 배포 직전이나 런타임에야 드러날 수 있다.
- 순환 의존성도 마찬가지로, 컴파일 타임에 강제하지 않으면 예기치 않은 순서로 로드되며 버그로 이어질 수 있다.

따라서 "테스트로만 검증하는 모듈화"를 넘어 **컴파일러/빌드가 보장하는 경계**를 고려하는 것이 이 문서의 목적이다.

## 5. SSOTA에서 취할 수 있는 중간 지점

Gradle 멀티모듈을 그대로 Next.js/TS에 적용할 수는 없지만, **물리적 경계에 가깝게** 가져가는 방법들이 있다.

### 5.1 Turborepo 패키지 분리

- 도메인(또는 도메인 그룹)을 `packages/domain-*` 형태의 **별도 패키지**로 분리.
- `package.json`의 `dependencies`에 다른 패키지만 명시적으로 넣으면, 그게 곧 허용된 의존성 그래프가 됨.
- 허용되지 않은 패키지를 import 하면 **빌드/타입 체크 단계**에서 발견 가능.

### 5.2 TypeScript Project References

- `tsconfig.json`의 `references`와 `composite: true`로 프로젝트를 여러 개로 쪼갬.
- 도메인별(또는 레이어별)로 참조 관계를 제한하면, **타입 체크/빌드 시** 잘못된 참조가 드러날 수 있다.

### 5.3 ESLint boundaries / import 제한

- `eslint-plugin-boundaries` 또는 `import/no-restricted-paths` 등으로  
  "이 디렉토리에서는 저 디렉토리로 import 금지" 규칙을 두고 CI에서 실패시키기.
- 컴파일 타임은 아니지만 **CI 타임**에 즉시 피드백 가능.

### 5.4 package.json `exports` 필드

- 도메인을 패키지로 분리한 경우, `exports`로 **공개 API만** 노출.
- 내부 구현을 import 하면 resolution 실패로 빌드/런타임 에러가 나도록 유도.

---

## 6. 정리

- **논리적 경계**: 폴더와 컨벤션으로만 구분. 컴파일러는 경계 위반을 막지 못함.
- **물리적 경계**: 빌드/패키지 시스템이 의존성을 선언한 것만 허용. 위반 시 **컴파일/빌드 실패**로 즉시 피드백.
- SSOTA는 현재 **논리적 경계** 기반이므로, 도메인이 늘어날수록 **의존성·순환 참조·AI 생성 코드**에 대한 리스크를 줄이려면 5장의 중간 지점(패키지 분리, TS references, ESLint boundaries 등)을 단계적으로 도입하는 것을 권장한다.

이 문서는 "테스트 통과를 넘어, 컴파일러가 보장하는 모듈화"를 고민할 때 참고할 수 있도록, flex팀의 Gradle 기반 물리적 분리 사례와 SSOTA 구조를 비교해 정리한 것이다.
