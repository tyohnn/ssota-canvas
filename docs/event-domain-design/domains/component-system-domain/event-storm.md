# Component System Domain - Event Storm

## 🎯 도메인 이해: 추상적 사고를 위한 재사용 가능한 개념 정의

**비즈니스 가치**: 반복되는 사고 패턴을 컴포넌트화하여 체계적이고 일관된 추상화 작업 지원

---

## 📋 정제된 이벤트 목록

### 컴포넌트 생성 및 관리
- 컴포넌트 블럭이 정의되었다 (Component Block Defined)
- 일반 블럭이 컴포넌트 블럭으로 변환되었다 (Block Converted to Component)
- 컴포넌트 블럭이 삭제되었다 (Component Block Deleted)
- 컴포넌트 블럭의 커스텀 속성이 정의되었다 (Component Custom Property Defined)

### 인스턴스 생성 및 동기화
- 인스턴스 블럭이 생성되었다 (Instance Block Created)
- 인스턴스 블럭이 컴포넌트와 동기화되었다 (Instance Block Synced with Component)
- 인스턴스가 일반 블럭으로 분리되었다 (Instance Detached to Regular Block)
- 개별 인스턴스가 분리되었다 (Single Instance Detached from Component)

### 속성 오버라이드 관리
- 인스턴스 블럭의 속성이 오버라이드되었다 (Instance Property Overridden)
- 인스턴스 블럭 속성이 리셋되었다 (Instance Property Reset)
- 오버라이드 상태가 시각적으로 표시되었다 (Override Status Visualized)
- 오버라이드 값이 최종 속성으로 고정되었다 (Override Values Finalized)
- 인스턴스 속성이 일반 블럭으로 변환되었다 (Instance Properties Converted to Regular Block)

### 컴포넌트 스타일 시스템
- 컴포넌트 블럭 스타일이 속성값과 연동되었다 (Component Style Linked to Property Value)
- 스타일-속성 연동 규칙이 생성되었다 (Style–Property Link Rule Created)
- 스타일-속성 연동 규칙이 변경되었다 (Style–Property Link Rule Modified)
- 스타일-속성 연동 규칙이 삭제되었다 (Style–Property Link Rule Deleted)

### 엣지 및 연결 관리
- 컴포넌트 엣지가 정의되었다 (Component Edge Defined)
- 컴포넌트 엣지가 인스턴스에 적용되었다 (Component Edge Applied to Instance)

### 컴포넌트 생명주기 관리
- 컴포넌트 삭제가 요청되었다 (Component Deletion Requested)
- 인스턴스 변환이 시작되었다 (Instance Conversion Started)
- 모든 인스턴스가 변환되었다 (All Instances Converted)
- 컴포넌트가 삭제되었다 (Component Deleted)
- 인스턴스 분리가 요청되었다 (Instance Detachment Requested)
- 인스턴스 분리가 완료되었다 (Instance Detachment Completed)

## 🔥 핫스팟 (Hot Spots) - 해결해야 할 문제점들

### 1. **속성 동기화의 복잡성** 🚨
**문제**: 컴포넌트 변경 시 수많은 인스턴스들의 속성 동기화 처리
- 어떤 속성이 오버라이드되었는지 추적 필요
- 컴포넌트 속성 삭제 시 인스턴스 오버라이드 처리
- 동기화 실패 시 일관성 보장 방법

**영향도**: 매우 높음 - 데이터 일관성 문제로 이어질 수 있음

### 2. **컴포넌트 삭제 시 인스턴스 처리** 🚨  
**문제**: 컴포넌트가 삭제되면 모든 인스턴스를 일반 블럭으로 변환
- 대량 인스턴스 처리 시 성능 이슈
- 변환 과정에서 데이터 손실 가능성
- 사용자에게 변환 결과 알림 필요

**영향도**: 높음 - 사용자 경험과 시스템 안정성에 직결

### 3. **오버라이드 상태 관리** ⚠️
**문제**: 어떤 속성이 오버라이드되었는지 사용자와 시스템이 명확히 구분
- UI에서 시각적 구분 표시 복잡성
- 부분 오버라이드 상태 추적
- 오버라이드 이력 관리

**영향도**: 중간 - UX 복잡성 증가

### 4. **스타일-속성 연동 규칙의 순환참조** ⚠️
**문제**: 속성값에 따른 스타일 변경 시 무한 루프 가능성
- 속성 A가 색상을 변경하고, 색상 변경이 속성 B를 변경하는 경우
- 규칙의 우선순위와 실행 순서

**영향도**: 중간 - 시스템 안정성 이슈

### 5. **개별 인스턴스 분리의 복잡성** ⚠️
**문제**: 특정 인스턴스만 컴포넌트에서 분리할 때의 데이터 처리
- 오버라이드된 속성의 최종 값 고정 처리
- 분리 후 컴포넌트 동기화에서 제외하는 로직
- 분리된 인스턴스와 일반 블럭의 구분

**영향도**: 중간 - 데이터 일관성과 사용자 경험에 영향

- AI 기반 컴포넌트 후보 추천

**메모**: 향후 구현 검토 필요

## 🎨 실제 사용 시나리오 (수정된)

### 시나리오: Event Storming 워크샵에서 "이벤트 블럭" 컴포넌트 생성

#### Step 1: 이벤트 블럭 정의
```
사용자가 "주문이 접수되었다" 텍스트 블럭을 생성
├── 스타일: 주황색 배경, 둥근 모서리
├── 기본 속성: 텍스트 내용, 위치, 크기  
└── 커스텀 속성: 
    ├── 서브도메인: 선택형 (주문관리, 결제, 배송...)
    ├── 우선순위: 선택형 (높음, 중간, 낮음)
    └── 담당자: 텍스트형
```

#### Step 2: 컴포넌트화
```
"이벤트 블럭"을 컴포넌트로 변환
├── 원본 블럭 → 인스턴스 블럭으로 자동 변환
├── 컴포넌트 블럭 생성 (캔버스에 보이지 않음)
└── 커스텀 속성들도 컴포넌트에 포함
```

#### Step 3: 스타일-속성 연동 규칙 설정
```
스타일 연동 규칙 정의:
├── 서브도메인이 "주문관리"이면 → 파란색 배경
├── 서브도메인이 "결제"이면 → 초록색 배경  
├── 우선순위가 "높음"이면 → 굵은 테두리
└── 우선순위가 "낮음"이면 → 점선 테두리
```

#### Step 4: 인스턴스 생성 및 커스터마이징
```
새로운 이벤트 생성 시:
├── 컴포넌트에서 인스턴스 생성
├── 기본값으로 동기화
├── 사용자가 속성 오버라이드:
│   ├── 텍스트: "결제가 완료되었다" 
│   ├── 서브도메인: "결제" (자동으로 초록색 배경 적용)
│   └── 담당자: "김개발" (오버라이드)
└── 위치, 크기는 페이지별로 독립적으로 설정
```

#### Step 5: 컴포넌트 업데이트
```
이벤트 블럭 컴포넌트 수정:
├── 새 커스텀 속성 추가: "비즈니스 임팩트" (높음/중간/낮음)
├── 스타일 규칙 추가: 임팩트가 "높음"이면 → 빨간 테두리
└── 모든 인스턴스에 자동 동기화:
    ├── 오버라이드되지 않은 속성들만 업데이트
    ├── 새 속성 "비즈니스 임팩트"는 기본값으로 추가
    └── 기존 오버라이드 속성들은 그대로 유지
```

#### Step 6: 개별 인스턴스 분리
```
특정 인스턴스가 너무 특수해진 경우:
├── 사용자가 "이 인스턴스는 독립적으로 관리하고 싶어"
├── 개별 분리 요청 → Detach Instance from Component
├── 오버라이드된 모든 값이 최종 속성으로 고정:
│   ├── 텍스트: "결제가 완료되었다" (고정)
│   ├── 서브도메인: "결제" (고정)
│   └── 담당자: "김개발" (고정)
├── 더 이상 컴포넌트 동기화 영향 받지 않음
└── 다른 인스턴스들은 여전히 컴포넌트와 연결 유지
```

## 🎯 핵심 비즈니스 가치

1. **체계적 사고 지원**: 일관된 형태의 사고 도구 제공
2. **생산성 향상**: 반복되는 개념 정의 작업 자동화  
3. **협업 효율성**: 팀 내 공통 개념과 스타일 가이드 공유
4. **확장성**: 새로운 사고 패턴을 쉽게 정의하고 적용
