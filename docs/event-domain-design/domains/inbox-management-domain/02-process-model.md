## 🎯 Process Modeling Overview
Inbox Management Domain의 핵심 프로세스를 실제 상호작용 순서에 따라 정의

### 📝 작성 원칙 (하이브리드 접근법)

#### ✅ 항상 작성해야 할 내용 (비즈니스 프로세스)
- 비즈니스 정책 및 규칙
- 권한 기반 필터링 로직
- 시스템 처리 흐름
- 데이터 검증 규칙
- 외부 시스템 통합

#### ✅ 선택적으로 작성 가능 (최소 UX 힌트)
- `*UI Hint:` 형태로 Frontend 팀을 위한 최소 힌트 제공
- 예시: `*UI Hint: 옵션 선택 UI*`, `*UI Hint: 확인 다이얼로그*`
- 원칙:
  - **최소성**: 꼭 필요한 힌트만
  - **추상성**: 구체적 컴포넌트 이름 금지
  - **선택성**: `*` 표시로 선택적 정보임을 명시

#### ❌ 작성 금지 (UI 과도 종속)
- 버튼 위치, 색상, 크기
- 애니메이션, 트랜지션 효과
- 구체적인 컴포넌트 이름 (Material-UI Select, shadcn/ui Dialog 등)
- 반응형 레이아웃 세부사항

> **참고**: 구체적인 UI/UX 설계는 `03-user-flow.md`에서 진행합니다.

### 🔄 시퀀스 기반 상호작용 순서
각 시나리오는 여러 시퀀스로 구성되며, 이벤트에 의해 다음 시퀀스가 트리거됩니다:

**Event** → **Policy** → **Read Model** → **Command** → **System** → **Event** → **Policy** → ...

1. **Event** (이전 시퀀스의 결과) → 2. **Policy** (이벤트에 따른 정책 적용) → 3. **Read Model** (시스템에서 사용자에게 제공하는 정보) → 4. **Command** (사용자가 입력하는 정보) → 5. **System** (처리 시스템) → 6. **Event** (결과 이벤트)

> **Command 구분**: Process Model의 **Command**는 “사용자 의도/입력”(예: Inbox 진입 요청)을 의미합니다. **03-software-design** 단계에서는 System이 이를 수신해 Aggregate에 전달할 **도메인 명령**(예: Create Inbox Session, Restore Inbox Session)으로 구체화하며, Aggregate는 해당 명령을 처리한 뒤 **Event**를 발행합니다.

### 🟪 External Systems

Inbox Management는 다음 외부/타 도메인 시스템과 연동합니다. Process Model에서는 **연동 시점·책임**만 정의하며, 각 시스템 내부 플로우는 해당 도메인에서 정의합니다.

| 시스템 | 유형 | 역할 | SSOT | 통합 방식 |
|--------|------|------|------|-----------|
| **Source Domain - Job System** | 타 도메인 | 추출/요약 비동기 처리 | Source 도메인이 Job·추출 결과의 SSOT | Inbox가 Source Job 등록 API 호출; 완료/실패 시 콜백 또는 폴링으로 상태 반영 |
| **Block Management - Block System** | 타 도메인 | 소스 → Block 생성, 타입 검증 | Block Management가 Block SSOT | 동기 API 호출 (Block 생성 후 inbox_message에 block_id 연결) |
| **Workspace Management - Page System** | 타 도메인 | 페이지 목록 조회, 권한 검증 | Workspace가 Page·권한 SSOT | RLS, 페이지 목록 API 조회 |
| **Canvas Management - Block Mount System** | 타 도메인 | Block을 Page에 마운트 | Canvas가 마운트 위치 SSOT | 동기 API 호출 (사용자 페이지 선택 시) |
| **AI Management - Recommendation System** | 타 도메인 | LLM 기반 페이지 추천 생성 | AI가 추천 결과 생성; Inbox가 수신 사실 보유 | AI 서비스 호출 (동기 또는 비동기); 결과 수신 시 **Page Recommendations Generated by LLM** 발행 |
| **Storage (Supabase)** | 서드파티 | 파일/오디오 업로드 저장 | Storage가 파일 바이너리 SSOT | 업로드 URL 획득 후 Block·Source Job에 전달 |

## 📍 Scenario 0: Source Domain Job 결과 반영 (동기화)

Inbox는 Source Domain에 Job을 등록한 뒤, Job 완료/실패 결과를 수신하여 Inbox 메시지 처리 상태를 갱신합니다.

### Sequence 1: Source Job 완료/실패 콜백 수신 시 Inbox 메시지 상태 반영

**Trigger Event**: Source Domain에서 Job 완료 또는 실패 알림 수신

```
🔗 Source Domain - Job System: "Job이 완료되었거나 실패했어"
```

**Policy**:
- "Whenever Source Job 완료 알림 수신됨, then always 해당 Inbox 메시지 처리 상태를 요약완료로 갱신하기"
- "Whenever Source Job 실패 알림 수신됨, then always **Inbox Message Processing Failed** 발행하기"
- 재시도는 **Message Queue 시스템**에서 자동 처리(재시도 횟수·간격 등); Inbox는 완료/실패 콜백만 반영

**Read Model** (시스템에서 사용자에게 제공하는 정보):
- 메시지별 처리 상태 (업로드됨 / 추출중 / 요약완료 / 실패)
- *UI Hint: 상태 표시 영역*

**Command**: (이 시퀀스는 시스템 간 콜백으로 트리거됨; 사용자 Command 없음)

**System**: Inbox - Source Job Result Handler (Backend)
- 비즈니스 로직: 워크스페이스 격리 확인, 메시지·Job 매핑 검증
- 검증 로직: 콜백 페이로드 검증, idempotency key로 중복 처리 방지
- 처리 로직: 메시지 상태 갱신, 실패 시 **Inbox Message Processing Failed** 이벤트 발행

**Events**:
1. (성공 시) 메시지 상태가 요약완료로 갱신됨 (도메인 내 별도 이벤트 없이 Read Model 갱신)
2. (실패 시) **Inbox Message Processing Failed**

## 📍 Scenario 1: Inbox 세션 생성 및 메시지 추가

### Sequence 1: 사용자 /inbox 진입 시 세션 생성 또는 복원

**Trigger Event**: 사용자 Inbox 진입 요청

```
👤 사용자: "/inbox에 들어가서 Quick Capture을 쓰고 싶어"
```

**Policy**:
- "Whenever Inbox 진입 요청됨, then always 워크스페이스 권한 검증하기"
- "Whenever 권한 검증 통과함, then always 기존 활성 세션이 있으면 복원하고 없으면 새 Inbox 세션 생성하기"
- "Whenever Inbox 세션 생성/복원 완료됨, then always **Inbox Session Created** 발행하기"

**Read Model** (시스템에서 사용자에게 제공하는 정보):
- 현재 워크스페이스 내 Inbox 세션 존재 여부 및 세션 ID
- 세션에 속한 메시지 목록 (없으면 빈 목록)
- *UI Hint: 채팅형 Inbox 화면*

**Command**: Inbox 진입 요청 (사용자가 입력하는 정보)
- (암묵) 현재 워크스페이스 컨텍스트
- *Software Design 시*: System이 이 요청을 수신한 뒤 도메인 명령으로 **Create Inbox Session** 또는 **Restore Inbox Session**을 발행하여 Aggregate가 처리하고, 결과로 **Inbox Session Created** 이벤트 발행

**System**: Inbox Session Manager (Backend - Security Enforcement)
- 비즈니스 로직: 워크스페이스 격리, 세션 생성/복원 규칙
- 검증 로직: 워크스페이스 권한, RLS
- 처리 로직: (진입 요청 수신 → Create/Restore 도메인 명령 처리 →) 세션 생성 또는 복원, **Inbox Session Created** 발행

**Events**:
1. **Inbox Session Created**

### Sequence 2: 사용자가 소스 인입 시 메시지 추가 및 Block 생성·Source Job 등록

**Trigger Event**: Inbox Session Created (또는 기존 세션 복원 완료)

**Policy**:
- "Whenever 세션 준비됨이고 사용자가 소스 인입함, then always 해당 워크스페이스·세션에 Inbox 메시지 추가하기"
- "Whenever Inbox 메시지 추가 요청됨, then always Block Management에 Block 생성 요청한 뒤 생성된 Block으로 메시지 연결하기"
- "Whenever Block 연결 완료됨, then always Source Domain에 Source Job 등록하기 (추출/요약 비동기)"
- "Whenever 메시지 추가 및 Job 등록 완료됨, then always **Inbox Message Added** 발행하기"

**Read Model** (시스템에서 사용자에게 제공하는 정보):
- 소스 타입별 업로드/입력 옵션 (파일, 링크, 오디오, 메모 등)
- 업로드 진행 상태 및 완료 여부
- *UI Hint: 업로드/붙여넣기 입력 영역*

**Command**: Inbox 메시지 추가 요청 (사용자가 입력하는 정보)
- 소스 타입 (파일/링크/오디오/메모/유튜브 등)
- 소스 데이터 (파일 참조, URL, 텍스트 등)
- (암묵) 세션 ID, 워크스페이스 ID

**System**: Inbox Message Manager + Block Management - Block System + Source Domain - Job System (Backend)
- 비즈니스 로직: 즉시 Block 생성으로 성공감 제공, 추출/요약은 비동기; 워크스페이스·세션 격리
- 검증 로직: 소스 타입·크기 제한, Block 생성 결과 검증, Job 등록 파라미터
- 처리 로직: Block 생성 요청 → block_id 연결 → Source Job 등록 → **Inbox Message Added** 발행

**Events**:
1. **Inbox Message Added**

## 📍 Scenario 2: 페이지 추천 결과 수신

### Sequence 1: AI 호출 후 페이지 추천 결과 수신 및 발행

**Trigger Event**: 요약 완료 등 조건 충족 후 AI Management에 페이지 추천 요청이 수행됨

```
🔧 시스템: "LLM 페이지 추천 API 호출 후 결과를 수신했어"
```

**Policy**:
- "Whenever AI 서비스가 페이지 추천 결과를 반환함, then always 해당 결과를 Inbox 도메인에 반영하고 **Page Recommendations Generated by LLM** 발행하기"
- "Whenever 추천 요청이 실패함, then always 사용자에게 재시도 또는 수동 선택 옵션 제공하기 (Read Model)"
- "같은 세션 메시지는 약한 맥락 힌트로만 활용; 자동 확정 없음"

**Read Model** (시스템에서 사용자에게 제공하는 정보):
- 메시지(Block)별 페이지 추천 후보 n개 (제목, 추천 이유, 확신도)
- 추천 미생성/실패 시 상태 및 재시도 옵션
- *UI Hint: 추천 배지, 배지 클릭 시 페이지 선택*

**Command**: (이 시퀀스는 시스템 처리 결과로 트리거됨. 사용자 선택은 다음 시퀀스에서 Block Mount로 이어짐)
- 사용자 페이지 선택 시 → Canvas Management - Block Mount System 호출 (Scenario 2 연계, 상세는 Canvas/Block Mount 도메인)

**System**: Inbox - Page Recommendation Handler + AI Management - Recommendation System (Backend)
- 비즈니스 로직: 워크스페이스·세션 격리, 추천 개수(n) 적용, 세션 맥락은 선택적 전달
- 검증 로직: AI 응답 스키마 검증, 권한(페이지 목록 조회 결과)과 일치 여부
- 처리 로직: AI 호출 결과 수신 → **Page Recommendations Generated by LLM** 발행

**Events**:
1. **Page Recommendations Generated by LLM**

## 📍 Scenario 3: 처리 실패 시 상태 반영

### Sequence 1: Inbox 메시지 처리 실패 시 상태 표시

**Trigger Event**: Source Job 실패 알림 수신 (Scenario 0 Sequence 1에서 **Inbox Message Processing Failed** 발행됨)

**Policy**:
- "Whenever **Inbox Message Processing Failed** 발행됨, then always 해당 메시지를 실패 상태로 표시하기"
- "실패 원인은 Read Model에 노출 가능; 상세는 로그/모니터링용"
- 재시도는 **Message Queue 시스템**에서 자동 처리되며, Inbox에서는 사용자 재시도 액션을 제공하지 않음

**Read Model** (시스템에서 사용자에게 제공하는 정보):
- 실패한 메시지 목록 및 상태
- *UI Hint: 상태 표시 영역*

**Command**: (사용자 액션 없음; 실패 상태 조회만 가능)

**System**: Inbox - Source Job Result Handler (Backend) — 실패 콜백 수신 시 이미 Scenario 0에서 처리; 본 시퀀스는 해당 상태를 사용자에게 보여주는 Read Model 관점

**Events**:
- (추가 이벤트 없음; **Inbox Message Processing Failed**는 Scenario 0에서 발행됨)

## 💡 핵심 Policy 정리

### Source Domain 연동
1. **Job 결과 반영**: Source Job 완료/실패 콜백 수신 시 즉시 Inbox 메시지 상태 갱신
2. **실패 시 이벤트**: 실패 수신 시 **Inbox Message Processing Failed** 발행
3. **재시도**: Message Queue 시스템에서 자동 처리; Inbox는 완료/실패 콜백만 반영 (사용자 재시도 불가)

### 세션 및 메시지
4. **즉시 Block 생성**: 업로드 즉시 Block 생성하여 성공감 제공; 추출/요약은 비동기
5. **워크스페이스 격리**: Inbox 세션·메시지는 워크스페이스 단위로 격리
6. **같은 세션 맥락**: 페이지 추천 시 세션은 약한 힌트로만 활용, 자동 확정 없음
7. **메시지 삭제**: 사용자 불가 (Inbox 메시지 삭제 기능 없음)

### 페이지 추천 및 마운트
8. **추천 + 사용자 선택**: 자동 마운트 없음; 추천 배지 클릭 시에만 Block Mount
9. **추천 실패 대응**: 추천 요청 실패 시 재시도 또는 수동 선택 옵션 제공

## 🔧 기술 권장사항

### Source Domain Job 연동
- **콜백/폴링**: Job 완료/실패 알림은 Webhook 또는 폴링으로 수신; idempotency key로 중복 처리 방지
- **재시도**: Message Queue 시스템에서 자동 처리; Inbox는 완료/실패 결과만 반영
- **모니터링**: Job 실패율, Inbox 메시지 처리 지연 모니터링

### 처리 상태 실시간 반영
- **폴링 또는 Realtime**: Supabase Realtime 구독 또는 폴링으로 상태 전파; 3~10초 내 첫 요약 표시 목표
- **낙관적 UI**: 업로드 즉시 카드 표시, 상태는 비동기 갱신

### 페이지 추천 및 성능
- **캐싱**: 사용자 Page 목록 캐싱으로 LLM 입력 준비 시간 단축
- **파이프라인**: 요약 완료와 추천 호출을 연속 파이프라인으로 처리해 지연 최소화

### Block·Canvas 연동
- **동기 호출**: Block 생성, Block Mount는 동기 API 호출; 타임아웃·재시도 정책 정의
- **고아 Block**: 마운트되지 않은 Block 정리 배치 또는 Soft Delete 정책은 Block/Canvas 도메인과 협의
